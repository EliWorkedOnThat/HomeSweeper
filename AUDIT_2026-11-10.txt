NEW FINDINGS
=====================================================================================

N1  HIGH  One listing can take the dashboard, the AI search and the blocked list down
    Where: Scraper/Derive.py first_int() (line ~137), called by derive() for the "Kati",
           "Kati (Numri i kateve)", "Banjo" and "Tualete" tags; with_derived() (line ~249) has no guard.
    What:  first_int() does int() on the first run of digits. Python refuses int() on more than
           4,300 digits (ValueError). derive() runs for every listing whenever the listings cache is
           rebuilt, so one such tag makes every rebuild fail.
    Evidence (DB copy + one listing with {"Kati": "1" x 5000}):
           GET /api/listings 500, POST /api/ai/search 500, GET /api/blocked 500, and they stay 500
           (the cache is never filled). The dashboard and the AI page are empty for that agent, and
           every agent who scraped the same listing gets the same. Agents can't delete the row.
    Caveat: not verified whether any site lets a seller type 4,300+ digits into a floor/bathroom
           field (Njoftime's fields are free text typed by the seller, and nothing caps them).
    Fix:   (a) first_int: read at most a few digits, e.g. re.search(r"-?\d{1,4}", ...), or catch
               ValueError and return None.
           (b) Defence in depth: in with_derived(), wrap derive() per listing (try/except -> log it and
               use derived = {}), so no future bug in one listing can blank the whole app.
           Retest: bigint.py must give 200 on all three endpoints.

N2  HIGH  "Jo agjenci" / "Person privat" drops every private seller on MerrJep and Njoftime
    Where: MerrJep_al/PlaywrightScraper1.py ATTRIBUTE_COLUMNS ("Njoftim nga" -> posted_by, line 38);
           njoftime_al/PlaywrightScraper3.py line ~541 (posted_by = "Kompani" or None);
           Scraper/Derive.py posted_by_of() (line ~206, only Duashpi gets "Person privat" for empty).
    What:  This answers B2. MerrJep's own tag tells the two apart: 176 listings say "Kompani" and 2 say
           "Person fizik" ("Bleona", and MerrJep's own sandbox test listing). So the "Kompani" values
           are right, but "Person fizik" is stored as-is and isn't one of the shared values
           (Search.POSTED_BY = "Kompani", "Person privat"). Njoftime marks only agencies and leaves
           private sellers empty, and Derive doesn't fill them in like it does for Duashpi.
    Evidence (real DB copy):
           AI posted_by = Person privat keeps: merrjep 0/178, njoftime 0/105, duashpi 35/105,
           gazetacelesi 50/105.
           Dashboard "Postuar nga": MerrJep shows a separate "Person fizik" option; Njoftime's 14
           private listings have no value, so ticking "Person privat" hides them.
    Why it matters: finding private sellers is the main reason agents buy this.
    Fix:   map "Person fizik" -> "Person privat" in the MerrJep scraper (the shared-wording rule) or in
           Derive; in posted_by_of(), treat empty as "Person privat" for njoftime too (same reason as
           Duashpi). Saved rows are corrected by Derive at read time, so no re-scrape is needed if it's
           done there. Also see #5: "Ina FutureHome" still passes Njoftime's name check as private.

N3  MEDIUM  Rentals stored as sales, and impossible sale prices
    Where: each scraper's listing_type mapping; Derive.derive() only sanity-checks rents (RENT_EUR_RANGE).
    Evidence (real DB, 493 listings):
      - Titles that say rent, stored as "Shitet": 4 on MerrJep ("JEPET ME QIRA APARTAMENT 2+1 - DON
        BOSKO" 750 €, "Apartament 2+1 me qira - 400 euro", "JEPET ME QERA ... 3+1" 500 ALL,
        "JEPET ME QERA 1+1+BALLKON ... 500 EURO"), 1 on Gazeta ("Jepet apartament me qera 3+1+2" 85.000 ALL).
      - 20 "sales" under 5.000 € (or 500.000 ALL), e.g. a villa at 5 €, an apartment at 175 ALL,
        five "Shitet apartament" at 2.700 €.
      - MerrJep's own test listing is stored as a real one ("Apartamente prej 80m2 test private",
        seller "Merrjep Sandbox Private Seller", upid 9837964).
    Effect: rent searches miss these, and "cheapest sales" starts with rentals and typos.
    Fix:   treat a sale under ~5.000 € like the rent check does (no price for filters/sorts), and flag
           a "Shitet" whose title says "jepet / me qira / me qera" (or let the title win). Skip sellers
           named "Sandbox" / titles with "test private" on MerrJep.

N4  MEDIUM (at 20k listings)  Every heart click rebuilds the whole listings cache
    Where: Scraper/Server.py api_favourite() -> forget_cached_listings() (line ~104 / ~596).
    What:  correct (tested: the change shows at once, API == DB after 343 parallel writes), but it
           throws away the derived copy of every listing. The next /api/listings, AI search or
           blocked-list request re-reads and re-derives all of them while holding LISTINGS_LOCK, so
           every other request waits.
    Evidence at 20,000 listings: /api/listings 2.4 s cached -> 4.9 s right after one heart click.
           Unnoticeable at today's ~500 listings.
    Fix:   under LISTINGS_LOCK, set listing["favourite"] on the cached dict instead of dropping the
           cache (set_favourite already committed it).

N5  LOW  The favourites page downloads every listing to show the favourites
    Where: UI/favourites.js loadFavourites() fetches /api/listings and filters favourite == true.
    Evidence: 20k listings, 20 favourites: 44 MB JSON (10 MB gzipped), 3.6 s before the 20 cards show.
    Fix:   with #4: /api/listings?favourite=1 (or the slim list endpoint).

N6  LOW  Two more quadratic regexes (same shape as #3), on short inputs today
    - njoftime_al/PlaywrightScraper3.py LEK_PRICE_PATTERN / EUR_PRICE_PATTERN (lines 111-112), run on
      the thread title: 4,000 digits 0.25 s, 8,000 digits 1.0 s (x4 per doubling).
    - Scraper/Derive.py PROPERTY_PATTERNS, the villa pattern "\d+ katesh" (line 61), run on the title and
      Kategoria on every cache rebuild: 10,000 digits 0.18 s, 20,000 digits 0.72 s.
    Titles on these sites are short, so neither is a problem today.
    Fix:   the same lookbehind as #3: (?<![\d.,'])(\d[\d.,']*)... and (?<!\d)\d+ katesh.

N7  LOW  The Excel export doesn't say which listings are favourites
    Where: Scraper/Output.py BASE_COLUMNS / HEADERS. Add "favourite" with an Albanian header
           (e.g. "E preferuar": Po/Jo). An "export only my favourites" option would also fit agents.

N8  LOW (before Phase 4)  The first real schema migration doesn't use the planned versioning
    Where: Scraper/DB.py create_tables() adds favourite by checking PRAGMA table_info.
    Tested: it works on an old DB and running it twice is harmless. But PRAGMA user_version is still 0
           and the DB isn't backed up first, which CLAUDE.md -> "Where files live" requires once agents
           have real data. Fine in dev; switch to user_version + ordered steps + backup before shipping.

N9  INFO  Small server details (harmless, noted so nobody re-investigates)
    - The 404 from no_windows_paths, the 403 from the Origin check and the 400 from the Host check
      carry no CSP / nosniff / no-cache headers (those middlewares sit outside no_stale_ui). The
      bodies are JSON, so nothing renders.
    - The Origin check compares host:port, not the scheme: https://127.0.0.1:8000 would pass, but
      nothing can serve that origin (the server on 8000 is plain HTTP).
    - HEAD /favourites and GET /favourites/ answer 404 (only GET /favourites is a route).

=====================================================================================
PRODUCT ASSESSMENT
=====================================================================================
As a customer (real estate agent):
- Real value: four sites in one place, phone numbers, Albanian AI search, blocked sellers, Excel,
  and now favourites, which agents will use daily.
- Friction:
  - "Jo agjenci" silently hides every private seller on two of the four sites (N2).
  - On a phone the first listing starts at 703 px of a 740 px screen on the dashboard (the favourites
    page does better: 351 px).
  - Operator controls (break, schedule, agency preference) sit in the agent's face (REVIEW.md #15).
  - The AI setup note tells agents to edit Data/anthropic_api_key.txt; errors say "Shiko konsolën e
    serverit"; "Mbledhja e fundit" has no date.
- What agents would pay more for: "new since yesterday" alerts, price-drop tracking, merging the same
  flat posted on several sites, export of the filtered set or of the favourites only.

As a business (unchanged):
- Agents in one office share one public IP; several copies scraping the same sites from one IP is the
  most likely way to get blocked. Stagger them, or plan a central scraper later.
- Legal check needed: storing private sellers' names and phone numbers falls under Albania's personal
  data protection law; each site has its own terms of use.
- AI cost: worst case ~$60 per agent per month at the $2/day cap. Build it into the price.
- Still undecided: the AI needs a key and contacts Anthropic, which contradicts "nothing phones home"
  and "no licence keys" in CLAUDE.md -> Product architecture.
- Owner installs on every PC: fine for ~20 agents, doesn't scale beyond that (code signing then needed).

As an engineer / QA:
- Scraper code still copied four times (~560-790 lines each); app.js 2,145 lines; all scraper state in
  module globals; everything derived at read time (which is why N1 and #4 hit every request).
- Still no automated tests.
